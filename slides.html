Validation de champ & d'objet

Problème métier

Un email institutionnel obligatoire

L'inscription doit être rejetée si l'email ne se termine pas par @ipssi.fr — avant tout enregistrement en base.

Concept DRF

validate_<champ>

  • Appelée automatiquement par is_valid() (convention de nom)
  • Doit retourner la valeur (jamais un booléen)
  • Erreur → raise serializers.ValidationError(...)
Code
def validate_email(self, value):
    if not value.endswith("@ipssi.fr"):
        raise serializers.ValidationError("Email IPSSI requis.")
    return value
❌ Erreur courante
def validate_email(self, value):
    if not value.endswith("@ipssi.fr"):
        return False   # jamais lu par is_valid()

Aucune erreur ne sera levée — False devient la valeur du champ.

✅ Correction
def validate_email(self, value):
    if not value.endswith("@ipssi.fr"):
        raise serializers.ValidationError("Email IPSSI requis.")
    return value   # toujours la valeur, jamais un bool
Problème métier

Confirmation de mot de passe

password et password_confirm doivent correspondre — impossible à vérifier champ par champ.

Concept DRF

validate(self, attrs)

  • Validation objet-level, reçoit tous les champs déjà validés
  • Doit retourner attrs en entier
  • Erreur ciblée : ValidationError({"champ": "..."})
Code
def validate(self, attrs):
    if attrs["password"] != attrs["password_confirm"]:
        raise serializers.ValidationError(
            {"password_confirm": "Les mots de passe ne correspondent pas."}
        )
    return attrs
❌ Erreur courante
def validate(self, attrs):
    if attrs["password"] != attrs["password_confirm"]:
        raise serializers.ValidationError("Erreur")
    # pas de return !

DRF lève un AssertionError : .validate() should return the validated data

✅ Correction
def validate(self, attrs):
    if attrs["password"] != attrs["password_confirm"]:
        raise serializers.ValidationError({"password_confirm": "..."})
    return attrs   # toujours renvoyer le dict complet
Problème métier

Quel code renvoyer ?

is_valid() échoue — quel status HTTP la vue doit-elle renvoyer ?

Concept DRF

Mécanismes déclaratifs

Problème métier

Empêcher les doublons d'email

Deux comptes ne doivent jamais partager le même email.

Concept DRF

validators=[...]

  • Mécanisme indépendant de validate_<champ>
  • Orchestré par is_valid(), jamais imbriqué dedans
  • ModelSerializer l'ajoute automatiquement si unique=True
❌ Erreur courante
def validate_email(self, value):
    if User.objects.filter(email=value).exists():   # double travail
        raise serializers.ValidationError("Email déjà utilisé.")
    return value
✅ Correction
email = serializers.EmailField(
    validators=[UniqueValidator(queryset=User.objects.all())]
)
Problème métier

Une salle, un seul créneau

Empêcher deux réservations sur la même salle à la même date — une contrainte sur deux champs combinés.

Concept DRF

Meta.validators + UniqueTogetherValidator

Équivalent objet-level et déclaratif — indépendant de validate().

❌ Erreur courante
class Meta:
    validators = [UniqueTogetherValidator(
        queryset=Booking.objects.filter(room=room),
        queryset=Booking.objects.filter(date=date),   # deux querysets !
    )]
✅ Correction
class Meta:
    validators = [UniqueTogetherValidator(
        queryset=Booking.objects.all(),
        fields=["room", "date"],
    )]
Problème métier

Réutiliser une règle sur 3 serializers

La règle « email @ipssi.fr » doit servir ailleurs sans copier-coller.

Concept DRF

Validator custom (classe)

  • État configurable à la construction (attribut d'instance)
  • DRF appelle validator(value) : un seul argument
  • ⚠️ Ne pas nommer sa classe EmailValidator (collision Django)
Code
class CompanyEmailValidator:
    def __init__(self, domain):
        self.domain = domain

    def __call__(self, value):
        if not value.endswith(self.domain):
            raise serializers.ValidationError(f"Domaine {self.domain} requis.")

Cycle de vie de l'objet

Problème métier

Ne pas redéclarer 10 champs

Le modèle User connaît déjà les types et contraintes.

Concept DRF

ModelSerializer

  • Introspection automatique (type, max_length, unique…)
  • extra_kwargs : ajuster sans redéclarer le champ
Code
class SignupSerializer(serializers.ModelSerializer):
    class Meta:
        model = User
        fields = ["email", "password"]
        extra_kwargs = {
            "password": {"write_only": True, "min_length": 8},
        }
Problème métier

Le mot de passe stocké en clair

Après inscription, le mot de passe apparaît lisible en base de données.

Concept DRF

save() vs create()

  • save() = dispatcher générique — ne jamais l'override
  • Il délègue à create() / update()
  • create_user() hash le mot de passe, Model.objects.create() non
❌ Erreur courante
def save(self, **kwargs):               # override du dispatcher
    data = self.validated_data
    data.pop("password_confirm")
    return User.objects.create(**data)  # mot de passe en clair
✅ Correction
def create(self, validated_data):
    validated_data.pop("password_confirm")
    return User.objects.create_user(**validated_data)  # hash auto

Champs avancés

Problème métier

Accepter en entrée, jamais en sortie

Le mot de passe doit être reçu à l'inscription mais jamais renvoyé par l'API.

Concept DRF

write_only / read_only

Asymétrie lecture/écriture — totalement indépendante du hashing (create_user).

❌ Idée fausse
Un PasswordField magique, ou un flag hidden=True…
ça n'existe pas.
✅ Correction
password = serializers.CharField(write_only=True)
Problème métier

Exposer un champ d'une relation

Afficher room.name sous la clé room_name, sans renommer le modèle.

Concept DRF

source

Remappe le nom exposé vers l'attribut réel — chemin à points possible.

Code
room_name = serializers.CharField(source="room.name", read_only=True)
Problème métier

Un message d'erreur clair pour l'étudiant

Le message générique DRF n'est pas assez explicite.

Concept DRF

error_messages via extra_kwargs

Code
extra_kwargs = {
    "email": {"error_messages": {"required": "L'email est obligatoire."}},
}
Problème métier

Modifier un seul champ (PATCH)

Un PATCH ne doit pas redemander tous les champs obligatoires.

Concept DRF

partial=True

  • Désactive uniquement le check « required » sur les champs absents
  • Un champ présent est toujours validé normalement
  • Auto-utilisé par partial_update() (PATCH)
Problème métier

Un champ qui n'existe pas dans le modèle

Afficher jours_restants, calculé à la volée.

Concept DRF

SerializerMethodField

Champ en lecture seule + méthode get_<champ>(self, obj) — obj = instance complète.

Code
jours_restants = serializers.SerializerMethodField()

def get_jours_restants(self, obj):
    return (obj.date - timezone.now().date()).days

Contexte & représentation

Problème métier

Savoir qui fait la requête

Le serializer doit connaître l'utilisateur connecté pour adapter sa réponse.

Concept DRF

context

  • context={"request": request} — un dictionnaire
  • Auto-injecté par get_serializer() dans les vues génériques
❌ Erreur courante
UserSerializer(data=request.data, context=request.user)
✅ Correction
UserSerializer(data=request.data, context={"request": request})
# puis :
self.context["request"].user
Problème métier

Fuite de données entre profils

Un profil affiche l'email des autres utilisateurs — bug de sécurité.

Concept DRF

to_representation()

Toujours super().to_representation(instance) d'abord, puis modifier data.

❌ Erreur courante
def to_representation(self, instance):
    data = self.to_representation(instance)        # RecursionError
    if self.context["request"].user == instance:    # condition inversée
        data.pop("email")
    return data
✅ Correction
def to_representation(self, instance):
    data = super().to_representation(instance)
    if self.context["request"].user != instance:
        data.pop("email")
    return data

Relations

Problème métier

Une commande, plusieurs articles

Créer Order et ses OrderItem en un seul POST.

Concept DRF

Serializer imbriqué en écriture

Jamais automatique — il faut override create().

❌ Comportement par défaut
ModelSerializer.create() ne sait pas transformer une liste de dicts en objets liés par clé étrangère.
✅ Correction
def create(self, validated_data):
    items_data = validated_data.pop("items")
    order = Order.objects.create(**validated_data)
    for item in items_data:
        OrderItem.objects.create(order=order, **item)
    return order
Problème métier

Un total sur toute la liste

Calculer une somme globale, pas commande par commande.

Concept DRF

many=True → ListSerializer

Logique globale : subclasser ListSerializer + Meta.list_serializer_class.

Code
class OrderListSerializer(serializers.ListSerializer):
    # ListSerializer.data enveloppe TOUJOURS le retour dans un ReturnList,
    # même si to_representation() renvoie un dict -> il faut surcharger
    # data lui-même, pas to_representation().
    @property
    def data(self):
        orders = super().data
        total = sum(o["amount"] for o in orders)
        return {"total": total, "orders": orders}

class OrderSerializer(serializers.ModelSerializer):
    class Meta:
        list_serializer_class = OrderListSerializer
Problème métier

Un lien plutôt qu'un identifiant brut

Dans une API publique, exposer une URL cliquable vers l'utilisateur.

Concept DRF

HyperlinkedModelSerializer

Relations rendues en URL vers la ressource — id remplacé par url.

Code
class OrderSerializer(serializers.HyperlinkedModelSerializer):
    class Meta:
        model = Order
        fields = ["url", "user", "amount"]
        # user -> "http://api/users/12/" au lieu de 12

Bilan

La grille à retenir

Méthode manuelleMécanisme déclaratif
Champvalidate_<champ>()validators=[...]
Objetvalidate()Meta.validators

Les deux colonnes s'exécutent toutes les deux, orchestrées par is_valid().

Deux idées fil rouge

save() ne construit rien

Il délègue à create()/update() — même logique qui sépare create_user() (hash) de write_only (visibilité).

Réutilisabilité

Valider dans le serializer (pas la vue) ; écrire des validators custom réutilisables entre serializers.

⚠️ Le piège à surveiller

Inventer un nom plausible quand on ne sait pas (ErrorHandler, PasswordField, hidden=True) au lieu de dire « je ne sais pas ».
